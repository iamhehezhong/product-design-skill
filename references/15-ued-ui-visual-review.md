# UI 视觉与交互落地检查

本文件将产品事业部 UED/UIUE 资料中的视觉细节、组件选型、适配要求和检查流程，整理为可直接用于产品设计、开发自查、测试走查和上线验收的补充规则。

## 适用范围

- Web、PC、移动端、小程序、H5、SaaS、CRM、工作台和后台系统。
- 设计稿、原型图、截图、录屏、HTML 页面和已上线系统。
- 设计、开发、测试、产品复核和上线前验收。

## 资料边界与优先级

- 本文件是现有 skill 的执行细化，不是另一套最高原则。
- [01-basic-principles.md](01-basic-principles.md) 以及现有 skill 已有规则优先。
- 如果本文件与现有 skill 的原则、评分规则或判断结论重复，不重复计算。
- 如果本文件与现有 skill 冲突，以现有 skill 为准；本文件只补充现有资料没有明确展开的检查方法、证据要求和组件级细节。
- 阈值是检查参考，不应脱离用户任务、内容长度、设备、平台和业务风险机械套用。
- 面向专业用户的系统可以使用行业标准术语、专业字段和常用缩写。检查重点是术语是否准确、统一、符合用户工作习惯，而不是术语是否“足够口语化”。

## 1. 评审前准备

开始检查前，尽量收集以下材料：

- 设计稿、交互说明、设计系统或组件规范。
- 实际页面、原型、HTML、录屏或截图。
- 目标设备、操作系统、浏览器、窗口尺寸和缩放比例。
- 用户角色、核心任务、权限范围和业务数据特征。
- 默认、加载、空、成功、失败、禁用、权限不足、网络异常和大量数据等状态。
- 变更前页面与变更后页面，或明确的预期效果。

如果只有一张静态截图：

- 可以检查布局、样式、文案、层级、对齐、间距和内容完整性。
- 不能据此确认点击反馈、加载性能、键盘操作、拖拽、权限、网络异常和恢复能力。
- 对无法确认的项目标记“待交互或运行时验证”，不要直接判定通过。

## 2. UI 变更检查闭环

### 2.1 先判断变更影响

将需求中的 UI 变更分为三类：

| 影响级别 | 判断方式 | 执行要求 |
|---|---|---|
| 无可感知影响 | 仅接口、后端逻辑、日志、埋点或内部性能优化，用户看不到界面变化 | 不需要 UI 走查 |
| 低影响 | 非核心流程的小范围变化，不改变大多数用户的操作习惯 | 建议完成自查，记录例外 |
| 高影响 | 核心流程修改、新增页面或模块、视觉风格变化、跨端适配、操作路径变化，或影响多数用户 | 提测前完成专项走查，并提供走查记录或变更前后对比 |

“微小”不等于“无影响”。只要用户能感知到位置、文案、组件、状态、反馈或操作路径变化，就应重新确认。

### 2.2 建议执行顺序

1. 设计或开发自查：对照预期效果和本清单逐项检查。
2. 专项走查：按“视觉问题”和“交互问题”分类记录。
3. 整改：按严重程度和业务风险排序修复。
4. 复核：检查实际修复结果，确认问题闭环。
5. 抽检：对已关闭需求进行定期抽样，观察重复问题是否减少。

### 2.3 最小问题记录

每条问题至少记录：

- 页面和模块。
- 具体位置和组件。
- 触发状态或使用条件。
- 实际效果。
- 预期效果。
- 违反的原则。
- 截图、录屏或运行环境证据。
- 严重程度、负责人、整改状态和复核结果。

建议将检查项标记为“通过 / 不通过 / 不涉及”。“不通过”必须有具体问题描述，“不涉及”必须说明为什么不适用。

## 3. 首轮快速筛查

对截图、原型或页面先做以下快速检查，优先发现确定性高、影响面大的问题：

1. 是否有遮挡、重叠、错位、溢出、无故截断或页面空白。
2. 是否有错误的层叠顺序、被裁切的阴影或边线。
3. 是否有双向滚动、过多同方向滚动或卡片、弹窗层级过深。
4. 是否有明显的颜色对比问题、字号过小、图片变形或模糊。
5. 是否有操作后无反馈、加载无状态、失败无原因、空状态无下一步。
6. 同类页面和组件是否出现样式、位置、顺序、交互或文案不一致。
7. 主要分辨率和内容长度变化时，核心区域是否稳定。

## 4. 视觉元素检查

### 4.1 样式完整与状态完整

逐一检查组件和图形的常规、悬停、聚焦、按下、选中、禁用、加载、成功和错误状态：

- 颜色、填充、边线、圆角、阴影、图标和文字均符合预期。
- 边线没有缺失、断裂、被遮挡或被裁切。
- 阴影没有被父容器裁切，也没有因相邻阴影过近而连成一片。
- 组件状态变化不会导致布局跳动、文字重新排版或操作入口突然消失。
- 交互前后没有与任务无关的结构和样式变动。
- 弹出内容、浮层、下拉菜单和提示不会被其他区域遮挡。

### 4.2 颜色与对比度

- 功能区域之间有足够的区分，导航、工作区、侧栏和辅助区域不会混成一片。
- 不同信息类别、状态和数据系列可以快速区分。
- 文字、图标、按钮与背景之间有足够对比度。
- 可参考 WCAG AA：普通文本与背景对比度不低于 `4.5:1`，大号文本不低于 `3:1`。如现有产品规范更严格，采用更严格规范。
- 正常、悬停、按下、禁用和选中状态都要检查对比度，不能只检查默认状态。
- 状态不能只依赖颜色，应同时使用文字、图标、形状、位置或样式变化。
- 不使用刺眼的强对比、厚重阴影或无语义的多种强调色破坏整体协调。

### 4.3 字体与文字

- 同一产品优先使用稳定的系统无衬线字体，并准备可显示特殊字符的字体回退。
- PC 中文正文通常不低于 `12px`；低于该值时必须在真实设备和目标分辨率验证可读性。
- 标题、区块标题、正文、辅助信息和标签应有稳定层级，不用大量加粗制造层级。
- 行间距一般可按字号的 `1.25-2` 倍作为参考；长文本、密集表格和移动端按实际可读性调整。
- 除非有明确语义，不使用倾斜、删除线等文字修饰。
- 字段标签应持续可见，不能只依赖占位文字。
- 字体、字重、字号、颜色、标点和对齐方式在同类页面保持一致。
- 品牌字体只在必要的品牌展示区域使用；网页自托管字体和改造字体应确认授权与版权风险。

### 4.4 图片、图标和图形

- 保持原始宽高比，禁止拉伸、压缩、变形和无意义裁切。
- 在不同页面、分辨率、设备和交互状态下，主体、文字和符号仍应清晰可辨。
- 图标线条粗细、视觉重心、尺寸和风格保持统一。
- 图片位、头像、视频封面和异常资源应有统一的缺省图。
- 透明背景图标和复杂图片应在保证质量的前提下控制体积，避免资源过大拖慢加载。
- 图形素材、人物肖像、品牌标识和字体应有合法来源或授权记录。

## 5. 布局、间距和对齐检查

### 5.1 对齐

- 元素沿明确的水平线、垂直线或网格排列，不出现轻微歪斜和无依据的错位。
- 同层级文本使用一致的对齐方式，不因页面局部调整而随意切换左对齐、居中或右对齐。
- 表单检查属性名、输入控件、说明文字和操作按钮的水平与垂直对齐。
- 表格检查表头与单元格、列与列、行内内容和操作按钮的对齐。
- 菜单项、按钮和图标中的文字应在视觉上居中，图标与文字的基线和间距稳定。

### 5.2 间距与边距

- 相关元素靠近，不相关元素拉开；间距应表达分组关系。
- 两个有边线的元素不要无间隔相连，尤其避免相邻圆角形成双边线或多余圆角。
- 两个有填充色的区域需要有清晰边界，不要因为贴合而看成一个整体。
- 文字、图标、按钮、表单、表格、菜单和分割线之间保持可辨识距离。
- 内容与屏幕、分栏、卡片、标题栏、按钮和输入框边缘保留稳定边距。
- 按钮内边距可将上下 `8-12px`、左右 `12-16px` 作为参考；按钮与分割线可将 `12-20px` 作为参考。若产品已有间距 token，优先使用 token。
- 交互热区不能因为视觉间距过小而容易误触；纯图标操作应扩大热区并提供名称或提示。

### 5.3 空间比例

- 业务工作区应获得与其价值匹配的空间，公共导航、装饰和低频入口不能挤压主任务。
- 不用大面积空白或大量卡片包装低价值内容。
- 页面、分栏、表单、表格和弹窗的宽高要同时满足内容完整、阅读舒适和操作效率。
- 组件的边线、圆角、阴影和内部内容应形成完整轮廓，不因父子容器关系出现残缺或拥挤。

## 6. 内容尺寸与信息完整性

以下为附件提供的内容适配参考值，实际使用以内容重要性、字体、设备和现有设计系统为准：

| 元素 | 参考检查点 |
|---|---|
| 标题 | 常规标题尽量控制在约 10 个中文字符内；过长时调整文案或层级，不要强行截断 |
| 字段名称 | 常规字段应能完整显示至少 5 个中文字符 |
| 单行输入框 | 常规宽度应能完整显示约 8-10 个中文字符 |
| 只读文本 | 一行优先容纳约 15-30 个中文字符，避免过宽或过早省略 |
| 文本域 | 每行可根据内容容纳约 10-50 个中文字符，保持阅读和编辑舒适 |
| 悬浮提示 | 内容较长时主动换行，避免形成过宽的提示框 |
| 表格 | 优先让对象名称、状态、金额、时间和下一步动作等关键字段完整可读 |

补充判断：

- 内容重要时，优先扩大容器、换行、分层或提供详情，不要直接截断。
- 必须省略时，使用省略号并提供完整内容的查看方式。
- 同一行内容高度差过大时，会破坏扫描节奏；按照项目或现有设计规范中更严格的行高要求执行。
- 不应因为容器固定高度导致文字溢出、重叠、遮挡或大量无意义换行。
- 页面不能在数据为空、接口失败或权限不足时只留下空白区域，应显示原因和下一步。

## 7. 适配、层级和性能

### 7.1 适配检查

桌面端至少检查项目指定尺寸；未指定时，建议覆盖 `1920`、`1440`、`1366` 和 `1280` 宽度，并验证：

- 窗口宽度变化时，核心工作区、导航、筛选、表格和操作栏不被挤压或错位。
- 内容数量增多、减少、变长、为空时，布局仍然稳定。
- 悬停、拖拽、浮起、展开和收起不会造成遮挡、截断、溢出或比例失衡。
- 图片、图标、图表和品牌标识在缩放时保持比例。
- 适配变化是必要且可解释的，不因实现方式导致无意义的位置跳动。
- 主流操作系统、浏览器内核、设备方向和项目要求的缩放比例下表现一致。

### 7.2 滚动、弹层和层叠

- 页面最外层不应同时出现无意义的水平和垂直滚动。
- 同一方向的滚动层级建议不超过 `2` 层；如现有 skill 或项目规范更严格，以更严格者为准。
- 弹窗、抽屉、下拉、提示和遮罩的层级顺序明确，内容不会被底层元素盖住。
- 能在页面内完成的轻量任务，不要用多层弹窗承载。
- 发现层级超过现有规则时，优先改为页面、抽屉、分步流程或上下文面板。

### 7.3 等待与性能反馈

- 项目已有性能 SLA 时，以项目 SLA 为准，并用真实设备或目标网络验证。
- 未定义 SLA 时，可将首屏 `1 秒内`作为较佳目标、`2 秒内`作为常规目标，完整页面加载尽量控制在 `3 秒内`。
- 预计超过 `2 秒`的区域应显示骨架屏或明确加载反馈；上传、导出、生成等长任务应显示进度、阶段或预计结果。
- 反馈不能只显示“加载中”，还应让用户知道系统是否已接收、当前处理到哪一步、失败后如何继续。

## 8. 组件选型与操作模式

组件不是装饰，应根据内容和任务选择，减少用户理解与操作成本：

| 场景 | 优先考虑 |
|---|---|
| 多条只读键值对 | 参数列表或结构化信息展示 |
| 多条同类对象 | 列表或表格 |
| 多级结构 | 树形控件 |
| 多级二维数据 | 树表格 |
| 少量字符输入 | 单行输入框 |
| 长篇单一文本 | 多行文本框 |
| 多个选项中选一个 | 单选框；选项较多时使用下拉单选 |
| 多个选项中选多个 | 复选框；选项较多时使用下拉多选 |
| 只有两个互斥选项且必须即时选择 | 开关 |
| 选项适合在当前区域完整展开 | 分段器 |
| 连续范围选择 | 滑块或调节器 |
| 日期或日期范围 | 日期选择器 |
| 下拉选项超过约 20 项 | 增加搜索、联想或分组 |

组件选型检查：

- 不要用输入框代替本可选择的固定选项。
- 不要用下拉框隐藏只有两项且需要立即理解的开关状态。
- 不要用卡片代替需要密集比较的表格。
- 不要用纯图标承载低频、抽象或高风险动作。
- 组件的触发、反馈、打开、关闭和切换方式在相同业务场景中保持一致。

## 9. 交互与状态完整性

### 9.1 每个重要操作都要有闭环

检查是否能顺利完成：

- 进入和离开。
- 选择和取消选择。
- 添加和移除。
- 新增、编辑、保存和删除。
- 查询、清空、排序、筛选和分页。
- 上传、预览、替换和删除文件。
- 提交、失败、重试和恢复。

### 9.2 反馈和帮助

- 悬停、聚焦、点击、拖拽和滚动有明确的视觉反馈。
- 操作后立即说明已接收、处理中、成功、失败或部分成功。
- 错误提示靠近发生错误的字段或操作，说明原因和可执行的修复方式。
- 普通提示、重要提示、气泡提示和系统通知的使用场景及位置保持统一。
- 复杂任务通常从 3 步及以上开始考虑操作向导或分步引导。
- 复杂操作、必填项、前置条件、限制、风险和专业但低频的元素，应在操作前或就近提供说明。
- 对默认无数据的列表显示明确空状态，并给出查询、创建、导入或调整筛选的入口。
- 有次数、额度或权限限制时，说明剩余次数、限制原因和超限后果。
- 新手说明应可关闭，并允许用户设置不再显示；不能持续打断熟练用户。
- 操作完成后，如存在明显的后续任务，应提供就近的下一步入口。

### 9.3 重点保护

- 输入格式、数据类型、长度、精度和范围应在输入阶段校验。
- 删除、支付、权限更改和其他不可逆动作提供必要的确认或验证。
- 高风险操作优先提供撤销、回退、取消、中断、恢复或自动保存。
- 失败时保留用户已输入内容和已完成工作。
- 自动化或批量操作应让用户预览影响范围，并支持人工接管。

## 10. 一致性检查

### 10.1 样式一致

- 同类按钮、选项卡、输入框、表格、卡片、弹窗和状态组件的颜色、圆角、边线、阴影、字号和尺寸一致。
- 常规、悬停、聚焦、按下、选中、禁用和加载状态都有统一表现。
- 同一语义的颜色和图形含义固定，例如成功、警告、错误、禁用和处理中不能随页面变化。

### 10.2 排版与位置一致

- 相同类型页面保持标题、说明、筛选、结果区、分页和操作区的基本布局。
- 数据管理操作通常集中在对应区域的操作位置，并只保留一个主按钮。
- 页面级提交操作在同类页面保持相同的区域、顺序和主次关系。
- 同类表单保持字段顺序、标签宽度、对齐方式、必填标记和初始提示语一致。
- 返回、关闭、查询、重置、导出、提交和取消等动作的入口位置和排序保持稳定。
- 如果因业务、内容或用户个性化需要例外，应记录例外原因，避免把例外扩散为新的不一致。

### 10.3 文案和数据格式一致

- 同一概念使用同一个名称，不混用简称、全称或近义词。
- 同一场景的语气、人称、句式、标点和提示格式保持一致。
- 专业术语保留其准确性；只修正不准确、未定义、内部化、混用或与结果不对应的术语。
- 中文界面不应出现无必要的英文、开发代码、接口报错或乱码；行业标准缩写和品牌名称可按产品约定保留。
- 金额、单位、日期、时间、状态、空值、百分比和小数精度保持统一。
- 数据录入格式与展示格式应相互对应，避免用户输入和结果展示采用不同规则。

## 12. 评审输出要求

- 先输出影响最大的视觉、交互和一致性问题，再输出细节问题。
